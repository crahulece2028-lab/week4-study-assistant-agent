# Study Assistant Agent - capstone report (task 4.4)

## 1. Overview

This report covers a single system built for the four Week 4 tasks: a **retrieval-augmented,
multi-step agent** over eight ECE lecture-note documents, with an evaluation harness and an
inspectable reasoning trace. Tasks 4.1 (RAG), 4.2 (workflow), 4.3 (observability/evaluation) and
4.4 (demo plus report) are one codebase, not four disconnected prototypes.

The system answers three kinds of question: those grounded in the notes (retrieve, grade, then
answer with a citation), those needing a calculation or a formula (a tool call), and small talk
(answered directly). It runs with **no API key** using a deterministic extractive generator, and
automatically upgrades to Groq or Gemini when a key is present.

Two parameters describe every reported run: `llm_mode = offline` and embeddings
`all-MiniLM-L6-v2`. The results below are therefore reproducible on any machine.

## 2. Retrieval (task 4.1)

**Corpus.** Eight generated lecture-note PDFs (reportlab, `data/build_corpus.py`) covering signals &
systems, digital electronics, control systems, communications, semiconductor devices, transmission
lines, microprocessors and DSP. Generated rather than downloaded so the repo is self-contained and
every retrievable fact is checkable by eye.

**Pipeline.** `PyPDFLoader -> RecursiveCharacterTextSplitter(800/150) -> all-MiniLM-L6-v2 (384-d,
L2-normalised) -> FAISS IndexFlatIP`. On this corpus: 8 documents, 27 chunks, mean chunk 652 chars
(`docs/ingest_stats.json`).

**Design choices.** Local CPU embeddings (no key, no cost, offline). `IndexFlatIP` over normalised
vectors gives exact cosine similarity - the right call at 27 chunks, where an approximate index would
add a recall knob for no benefit, and it makes the score in every trace a real cosine in [-1, 1].
`RecursiveCharacterTextSplitter` keeps chunks on paragraph boundaries and the overlap prevents an
answer straddling a split from being lost.

One engineering constraint shaped the code: the project lives under a non-ASCII path, which FAISS's
C++ `write_index` cannot open. `src/store.py` serialises the index to bytes and does the file I/O in
Python, which is Unicode-aware.

## 3. Agent workflow (task 4.2)

The agent is a LangGraph state machine (`src/graph.py`), compiled with a `MemorySaver` checkpointer.
Its topology is generated from the compiled graph itself, so the diagram cannot drift from the code.

```
START -> router -+-> retrieve -> grade -+-> generate -> END
                 |                      +-> rewrite -> retrieve   (bounded retry)
                 +-> tool ------> generate -> END
                 +-> direct ----> END
```

A graph is used rather than a chain because the flow is **conditional and cyclic**: routing is a
runtime decision, and a failed grade loops back through query rewriting. That cycle is the mechanism
the evaluation measures.

The LLM layer (`src/llm.py`) exposes four **decisions** - `route`, `grade`, `rewrite`, `generate` -
not a generic `invoke`. The graph does not know whether those come from a hosted model or the local
extractive implementation, which is what makes the no-key run a real system rather than a stub.

Tools (`src/tools.py`) are deliberately offline and two: a `calculator` that evaluates a numeric
expression through a **restricted AST walk** (never `eval`, because tool input is untrusted model
output), and a curated `formula_lookup` table that cites the source document.

## 4. Observability & evaluation (task 4.3)

**Method.** A 22-question labelled set: 16 single-hop, 2 out-of-scope, 4 deliberately hard. Each run
is scored on routing, retrieval hit, answer keywords, tool success, refusal correctness and latency.
Every node records a span: `eval/local_tracer.py` renders the offline run to `docs/traces/`, and with
`LANGSMITH_API_KEY` set `run_eval.py` also streams both configurations to LangSmith - 22 tagged trees
per configuration in the `week4-study-assistant` project, which `docs/langsmith_figures.py` pulls back
from the API to render `docs/traces/langsmith-*.png`. The set is additionally replayed through the
LangSmith evaluator harness as the dataset `week4-study-assistant-eval`
(`eval/langsmith_eval.py`), so the scores below are also stored and individually inspectable in
LangSmith.

**Results** (offline; median 56 ms/query, p95 68 ms, with remote tracing active):

| Metric | offline | llm (Groq `gpt-oss-20b`) |
|---|---|---|
| routing accuracy | 100% (22/22) | 100% |
| retrieval hit rate | 100% (14/14) | 100% |
| answer keyword rate | **93%** (13/14) | **100%** |
| tool success rate | 100% (4/4) | 100% |
| out-of-scope refusal rate | **67%** (2/3) | **100%** |
| latency (median) | 56 ms | 4.4 s (model time 3.4 s) |

**LLM run.** The identical set with a Groq-hosted model doing routing, grading and generation fixes
both offline failures (refusal 67% -> 100%, keyword 93% -> 100%) at a median ~4.4 s per query. The
repo default is `openai/gpt-oss-120b`; the free-tier daily cap on that model was exhausted by the
prompt comparison, so the final measured pass used its sibling `openai/gpt-oss-20b` through the same
code path. A first, unconstrained router prompt scored only **45% routing and 0% refusal** because the
model answered general-knowledge and out-of-scope questions from memory; aligning the router to the
agent's answer-from-the-notes contract fixed it. Full before/after in `docs/4.3_evaluation.md`.

**Reading the results honestly.** The three 100%s are a ceiling, not an achievement: the questions
were authored by the same person as the corpus and the offline grader is lexical, so retrieval over
8 short, topically-isolated documents is easy. The two informative metrics are the ones below 100%,
and both are analysed rather than hidden.

**Failure 1 (q20, refusal 67%).** "What is the formula for the Friis transmission equation?" - Friis
is absent from the corpus, but the words *transmission* and *formula* make retrieval return the
transmission-lines notes, and lexical relevance grading passes it. The agent then gives a fluent,
cited, wrong answer. Root cause: lexical overlap cannot separate "on the right topic" from "answers
the question". This is the clearest argument for a generative grader - and a generative (Groq) grader
does catch it: the hosted refusal rate is 100% (see `docs/4.3_evaluation.md`).

**Failure 2 (q22, keyword 93%).** Retrieval was correct; the extractive generator quoted a
neighbouring sentence about FM noise robustness instead of Carson's rule. A generation-ranking
failure, not a retrieval failure - the retrieval layer is performing better than the end-to-end
number implies.

**Ablation - chunking.** Re-indexed at 400/100, 800/150, 1200/240: hit@4 is 100% at every setting;
smaller chunks raise mean top-1 cosine (0.593 vs 0.517 at 1200/240) at the cost of ~3x the index
size. 800/150 is kept as a non-degenerate default; the choice is not performance-critical here.

**Ablation - retry policy.** The low-coverage floor detects "no lexical overlap at all" and skips the
retry loop. Off vs on: **8.0 -> 4.0 nodes** and **49 ms -> 22 ms** per unanswerable question, with
refusal correctness unchanged. The floor fixes a failure found in the first evaluation run, where the
naive agent retried questions it could never answer.

## 5. Demo (task 4.4)

`src/app.py` is a Streamlit chat UI that shows the answer, a confidence badge, the citations, and an
expandable **full agent trace** and retrieved chunks for every turn. The sidebar reports the live
backend, embedding model, retrieval settings and index stats, and explains the routing. Because the
point of the exercise is an inspectable process, the trace is front-and-centre, not hidden.

## 6. Design decisions and trade-offs

| Decision | Rationale | Cost |
|---|---|---|
| Local embeddings | no key/cost, offline, fast | smaller than a hosted embedding model |
| `IndexFlatIP` (exact cosine) | correct and simple at this scale | not built for millions of vectors |
| Decisions behind one LLM interface | whole system + eval run with no key | two code paths to keep in sync |
| Extractive offline generator | cannot hallucinate; stable eval target | quotes rather than synthesises |
| Offline tools | reproducible evaluation | no live web look-ups |
| Bounded retry + coverage floor | measured latency win | a floor threshold to justify |

## 7. Limitations and future work

- Small, self-authored corpus and test set; the 100% metrics are ceilings, not real-world estimates.
- A lexical relevance grader, which is the direct cause of the headline failure.
- Extractive default answering; the generative (Groq) baseline is reported in 4.3, matches the offline
  routing/retrieval on this set, and improves the two weak metrics (refusal 67% -> 100%, keyword
  93% -> 100%) at a median ~4.4 s vs 56 ms.
- Single-run measurements; the hosted router/grader vary slightly run to run (q10 mis-routes in some
  passes), and the measured hosted pass used `gpt-oss-20b` rather than the configured `gpt-oss-120b`.
- **Next steps, in priority order:** (1) repeat the traced pass on the configured `openai/gpt-oss-120b`
  after the Groq daily token cap resets, so the larger model's trees sit beside the 20b ones in
  LangSmith; (2) add a cross-encoder reranker and re-measure q22; (3) expand the corpus and test set
  beyond a single author; (4) add a web-search tool behind the same `TOOLS` interface.

## 8. Reproduction

```powershell
pip install -r requirements.txt
python data/build_corpus.py
python src/ingest.py
python src/graph.py "What is the Nyquist rate and why does it matter?"
streamlit run src/app.py
python eval/run_eval.py
python eval/improvement_experiment.py
```

Environment: Python 3.11, CPU only. No API key required. Set `GROQ_API_KEY` / `GOOGLE_API_KEY` /
`LANGSMITH_API_KEY` in `.env` to enable the hosted model and remote tracing.
