# 4.3 - Evaluation report

**Setup.** 22-question labelled set (`eval/testset.json`): 16 single-hop, 2 out-of-scope, and 4
deliberately hard (a two-document synthesis, an ECE-sounding formula that is *not* in the corpus, a
numeric lookup, and a rule-based estimate). The set is scored in **two configurations** so the engine
can be compared against itself:

- **offline** - no API key: deterministic extractive generator, lexical grader, local tracer.
  Reproducible on any machine: `all-MiniLM-L6-v2`, FAISS cosine, chunk 800/150, top-k 4,
  `MAX_RETRIES` 2, `LOW_COVER_FLOOR` 0.15.
- **hosted** - Groq `openai/gpt-oss-120b` as router, grader and generator, temperature 0. Same graph,
  same index, same chunking; **only the LLM changes.**

Reproduce: `python eval/run_eval.py` -> offline (`eval/summary.json`, `eval/results.json`,
`eval/results.csv`); `python eval/run_eval.py --suffix _llm` with `GROQ_API_KEY` set -> hosted
(`eval/summary_llm.json`, `eval/results_llm.json`, `eval/results_llm.csv`). The naive first hosted
run is kept as `eval/summary_llm_naive.json` (see "Hosted-LLM run" below).

## Headline

| Metric | offline | hosted (Groq) | Notes |
|---|---|---|---|
| routing accuracy | 100% | 100% | 22/22 in both |
| retrieval hit rate | 100% | 100% | 14/14 in-scope retrieval questions found the labelled document |
| answer keyword rate | **93%** | **100%** | 13/14 offline; the informative offline number |
| tool success rate | 100% | 100% | 4/4 (2 calculator, 2 formula) |
| direct (small-talk) rate | 100% | 100% | 1/1 |
| out-of-scope refusal rate | **67%** | **100%** | 2/3 offline; the other informative offline number |
| grounded-confidence rate | 100% | 93% | hosted flags q03 `low` (see grader note) |

## Read this first: why three 100%s are not a good result

Routing, retrieval-hit and tool accuracy are at 100% **because the evaluation set was written by the
same person who wrote the corpus, and the offline grader is lexical.** Retrieval over 27 chunks of
8 short, topically-isolated documents is an easy problem; the ceiling effect is visible in the
chunking ablation below, where hit@4 is 100% at every chunk size. The metrics that actually constrain
the design are the two that are *not* 100% - answer quality (93%) and the refusal decision (67%) -
and those are where the failure analysis lives. Treating the 100%s as evidence of a *good* RAG
system would be over-claiming; they are evidence that the plumbing is correct.

## Hosted-LLM run (Groq `openai/gpt-oss-120b`)

The identical 22 questions through the identical graph, with the router, grader and generator swapped
for the hosted chat model. Only the LLM changed.

| Metric | offline | hosted, naive prompt | hosted, aligned prompt |
|---|---|---|---|
| routing accuracy | 100% | **45%** | 100% |
| retrieval hit rate | 100% | **36%** | 100% |
| answer keyword rate | 93% | 86% | 100% |
| out-of-scope refusal | 67% | **0%** | 100% |
| grounded confidence | 100% | 29% | 93% |
| latency (median) | 26 ms | 1 300 ms | 17 620 ms |

**The first hosted run was worse, and the reason is the interesting part.** Given the naive router
prompt ("DIRECT = anything answerable without the notes"), the model sent every concept it already
knew - Nyquist, DFT resolution, quarter-wave matching - to `direct`, and answered out-of-scope
questions (World Cup, capital of France) from parametric memory instead of declining. Routing fell to
45% and the refusal rate to 0%: the agent had quietly stopped being a *grounded* assistant, which no
demo would have shown.

The fix was not a model change; it was making the router prompt state the agent's own contract -
"answer from the notes with a citation, never from memory; DIRECT is only greetings/meta; TOOL only for
a bare calculation or an explicit 'formula' request naming a known constant". With that, routing,
retrieval and refusal all return to their offline values and answer quality goes **up** to 100%.

The price is latency: median 17.6 s (`gpt-oss-120b` is a reasoning model on the free tier, ~5 s per
call, and a retrieval answer is 4 calls). The offline path is ~675x faster because it does no network
I/O. That is the real trade the two configurations make: **the hosted model buys robustness on hard,
long-tail questions; the offline path buys determinism and speed for CI.**

### The two graders fail in opposite ways

- **offline (lexical) grader** *under-rejects*: q20 (Friis, not in the corpus) shares the words
  "transmission" and "formula", clears the 0.4 coverage bar, and is answered instead of refused.
- **hosted (LLM) grader** *over-rejects*: q03 (Z-transform region of convergence) is a correct,
  cited hit, but the model judged the passages insufficient, so the answer is emitted `low`
  confidence even though it is right - the only non-`grounded` in-scope run (13/14).

Neither grader is simply "correct"; they bound the problem from both sides, which is the point of an
evaluation report rather than a demo.

## Failure analysis

### Failure 1 - q20, the Friis equation (refusal rate 67%)

> "What is the formula for the Friis transmission equation?"

`Friis` is **not in the corpus**, but the question contains *transmission* and *formula*, so:

1. the router sends it to `retrieve` (it is not a known formula key, so it is not a tool call);
2. retrieval returns the `06_transmission_lines` chunks, because "transmission" is a strong match;
3. the grader sees content-word coverage above the 0.4 threshold and marks it **relevant**;
4. `generate` answers with a real passage from the transmission-lines notes (Z0, reflections).

The answer is *plausibly wrong*: fluent, cited, and not an answer to the question. **Root cause:**
relevance is graded by lexical overlap, which cannot distinguish "the document is about the right
topic" from "the document answers the question". A generative grader (Groq/Gemini via `llm.grade`)
would likely catch this because it can reason about the answer rather than count shared words - which
is precisely the case for plugging a key in. It is the single most important limitation to state.

### Failure 2 - q22, FM bandwidth (answer keyword rate 93%)

> "How is the bandwidth of an FM signal estimated from its message and deviation?"

Retrieval **succeeded** (`04_communication_systems` was returned), but the extractive answer quoted
the neighbouring sentence about FM noise-robustness instead of Carson's rule. **Root cause:** the
offline generator ranks sentences by TF-IDF overlap with the question, and the Carson sentence
(`BW = 2*(delta_f + fm)`) shares few literal words with the question ("bandwidth ... estimated ...
message ... deviation"). A generative model with the same context would summarise the right sentence.
This is a generation-ranking failure, not a retrieval failure - worth separating, because it means
the retrieval layer is doing better than the end-to-end number suggests.

### What is *not* a failure

The two genuinely out-of-scope questions (q17 World Cup, q18 capital of France) are refused
correctly: near-zero lexical overlap trips the floor, the agent declines, and it is honest about why.

Both offline failure modes above are *fixed* by the hosted LLM: all three out-of-scope questions
(including q20) are refused (refusal rate 100%), and q22's Carson's-rule answer is produced correctly
(keyword rate 100%). They are failures of the *offline modules*, not of the agent's design - which is
why the report keeps the two configurations separate rather than reporting a single headline number.

## Ablation 1 - chunking

Re-indexed the same corpus at three settings and re-scored retrieval (`eval/improvement_chunks.json`).

| chunk / overlap | chunks | hit@4 | mean top-1 cosine |
|---|---|---|---|
| 400 / 100 | 48 | 100% | 0.593 |
| **800 / 150** | **27** | **100%** | **0.554** |
| 1200 / 240 | 17 | 100% | 0.517 |

**Finding:** hit@4 is saturated, so chunk size does not change *whether* the right document is found.
It does change how sharp the top match is - smaller chunks score higher cosine (more focused text) -
but at the cost of nearly twice the index size. 800/150 is kept as the default because it is the
middle of a flat, non-degrading curve: the choice is not performance-critical on this corpus, and
saying so is more useful than pretending it was tuned.

## Ablation 2 - retry policy

Ran the unanswerable questions with the low-coverage floor **off** (0.0) and **on** (0.15)
(`eval/improvement_retry.json`).

| Policy | mean nodes / question | mean latency |
|---|---|---|
| floor off (naive retry) | **8.0** | **49 ms** |
| floor on (this system) | **4.0** | **22 ms** |

**Finding:** the naive retry loop nearly doubles the work on questions it can never answer, because
the lexical grader cannot tell "bad query" from "absent topic" and keeps trying. The floor detects
near-zero overlap and skips straight to a low-confidence answer. Refusal correctness is unchanged
(100% on the questions this actually triggers for); only the wasted work disappears. This is the
concrete example of *measuring* a design decision rather than asserting it.

## Threats to validity

- **Small, self-authored set.** 22 questions and a same-author corpus. The 100% metrics are ceilings,
  not estimates of real accuracy.
- **Lexical grader.** "Relevant" means "shares content words", which is why two of the three
  interesting behaviours are failures.
- **Extractive generator.** Keyword recall is an easy bar for an extracting system; the hosted
  generative baseline is now reported alongside it, but on this easy set both reach the ceiling, so
  the comparison separates the *modules* more than it ranks the *models*.
- **Single run.** No variance/seed study. At temperature 0 and with a deterministic offline model the
  offline numbers are stable; the hosted run is a single pass at temperature 0, so its routing and
  grader decisions could still vary run to run.

## LangSmith

`src/config.py::enable_langsmith()` sets `LANGSMITH_TRACING` / `LANGSMITH_API_KEY` /
`LANGSMITH_PROJECT`, and `run_eval.py` calls it **before importing LangChain** so the tracing
instrumentation is active for the whole run. The local tracer remains the fallback when no key is set,
and the evaluation results do not depend on which tracer is active.

**Live traces.** With a personal access token in `.env`, `python eval/run_eval.py --suffix _ls`
uploaded one LangGraph trace per question to the `week4-study-assistant` project - 22 complete trees
(the `router / retrieve / grade / generate` path, plus the tool and refusal paths). `docs/langsmith_figures.py`
pulls them back **from the LangSmith API** and renders the real start/end waterfalls, each titled with
its trace id:

**Note on the hosted run.** The 22 traces above are the offline configuration, because its model calls
are local and free. A full *hosted* traced re-run was started, but the Groq free tier caps at 200 000

after the daily reset fills the project with the hosted trees too.
