# 4.3 - Evaluation report

**Setup.** 22-question labelled set (`eval/testset.json`): 16 single-hop, 2 out-of-scope, and 4
deliberately hard (a two-document synthesis, an ECE-sounding formula that is *not* in the corpus, a
numeric lookup, and a rule-based estimate). Run in the offline (no-key) configuration so the numbers
are reproducible on any machine: `all-MiniLM-L6-v2`, FAISS cosine, chunk 800/150, top-k 4,
`MAX_RETRIES` 2, `LOW_COVER_FLOOR` 0.15.

Reproduce: `python eval/run_eval.py` -> `eval/summary.json`, `eval/results.json`, `eval/results.csv`.

## Read this first: why three 100%s are not a good result

Routing, retrieval-hit and tool accuracy are at 100% **because the evaluation set was written by the
same person who wrote the corpus, and the offline grader is lexical.** Retrieval over 27 chunks of
8 short, topically-isolated documents is an easy problem; the ceiling effect is visible in the
chunking ablation below, where hit@4 is 100% at every chunk size. The metrics that actually constrain
the design are the two that are *not* 100% - answer quality (93%) and the refusal decision (67%) -
and those are where the failure analysis lives. Treating the 100%s as evidence of a *good* RAG
system would be over-claiming; they are evidence that the plumbing is correct.

## Failure analysis

### Failure 1 - q20, the Friis equation (refusal rate 67%)

> "What is the formula for the Friis transmission equation?"

`Friis` is **not in the corpus**, but the question contains *transmission* and *formula*, so:

1. the router sends it to `retrieve` (it is not a known formula key, so it is not a tool call);
2. retrieval returns the `06_transmission_lines` chunks, because "transmission" is a strong match;
3. the grader sees content-word coverage above the 0.4 threshold and marks it **relevant**;
4. `generate` answers with a real passage from the transmission-lines notes (Z0, reflections).

The answer is *plausibly wrong*: fluent, cited, and not an answer to the question. **Root cause:**
relevance is graded by lexical overlap, which cannot distinguish "the document is about the right
topic" from "the document answers the question". A generative grader (Groq/Gemini via `llm.grade`)
would likely catch this because it can reason about the answer rather than count shared words - which
is precisely the case for plugging a key in. It is the single most important limitation to state.

### Failure 2 - q22, FM bandwidth (answer keyword rate 93%)

> "How is the bandwidth of an FM signal estimated from its message and deviation?"

Retrieval **succeeded** (`04_communication_systems` was returned), but the extractive answer quoted
the neighbouring sentence about FM noise-robustness instead of Carson's rule. **Root cause:** the
offline generator ranks sentences by TF-IDF overlap with the question, and the Carson sentence
(`BW = 2*(delta_f + fm)`) shares few literal words with the question ("bandwidth ... estimated ...
message ... deviation"). A generative model with the same context would summarise the right sentence.
This is a generation-ranking failure, not a retrieval failure - worth separating, because it means
the retrieval layer is doing better than the end-to-end number suggests.

### What is *not* a failure

The two genuinely out-of-scope questions (q17 World Cup, q18 capital of France) are refused
correctly: near-zero lexical overlap trips the floor, the agent declines, and it is honest about why.

## Ablation 1 - chunking

Re-indexed the same corpus at three settings and re-scored retrieval (`eval/improvement_chunks.json`).

| chunk / overlap | chunks | hit@4 | mean top-1 cosine |
|---|---|---|---|
| 400 / 100 | 48 | 100% | 0.593 |
| **800 / 150** | **27** | **100%** | **0.554** |
| 1200 / 240 | 17 | 100% | 0.517 |

**Finding:** hit@4 is saturated, so chunk size does not change *whether* the right document is found.
It does change how sharp the top match is - smaller chunks score higher cosine (more focused text) -
but at the cost of nearly twice the index size. 800/150 is kept as the default because it is the
middle of a flat, non-degrading curve: the choice is not performance-critical on this corpus, and
saying so is more useful than pretending it was tuned.

## Ablation 2 - retry policy

Ran the unanswerable questions with the low-coverage floor **off** (0.0) and **on** (0.15)
(`eval/improvement_retry.json`).

| Policy | mean nodes / question | mean latency |
|---|---|---|
| floor off (naive retry) | **8.0** | **49 ms** |
| floor on (this system) | **4.0** | **22 ms** |

**Finding:** the naive retry loop nearly doubles the work on questions it can never answer, because
the lexical grader cannot tell "bad query" from "absent topic" and keeps trying. The floor detects
near-zero overlap and skips straight to a low-confidence answer. Refusal correctness is unchanged
(100% on the questions this actually triggers for); only the wasted work disappears. This is the
concrete example of *measuring* a design decision rather than asserting it.

## Threats to validity

- **Small, self-authored set.** 22 questions and a same-author corpus. The 100% metrics are ceilings,
  not estimates of real accuracy.
- **Lexical grader.** "Relevant" means "shares content words", which is why two of the three
  interesting behaviours are failures.
- **Extractive generator.** Keyword recall is an easy bar for an extracting system and a hard one to
  compare against a generative baseline, which was not run here (no key).
- **Single run.** No variance/seed study; at temperature 0 and with a deterministic offline model the
  numbers are stable, but this says nothing about a hosted model's run-to-run spread.

## LangSmith

`src/config.py::enable_langsmith()` sets `LANGSMITH_TRACING` / `LANGSMITH_API_KEY` /
`LANGSMITH_PROJECT`, and `run_eval.py` calls it **before importing LangChain** so the tracing
instrumentation is active for the whole run. To use it: put `LANGSMITH_API_KEY` and
`LANGSMITH_TRACING=true` in `.env` and re-run `python eval/run_eval.py`; the identical runs then
appear in the project named by `LANGSMITH_PROJECT`. The local tracer remains the fallback and the
evaluation results do not depend on which is active.
